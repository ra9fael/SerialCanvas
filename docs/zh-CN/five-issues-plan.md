# 五项问题的诊断与方案

分支：`feat/modernist-ui`。承接 `docs/layout-redesign.md`（`a142a48`）。

下文每一条结论都对照源码核实过，渲染相关的判断由 `audit/probe-sim-parse.mjs`
与 `audit/measure-buffer.mjs` 实测得出。**五项中有两项与报告不符**——它们被更正，
而不是按原样实施。

---

## 1. 日志每帧全量重建（真实缺陷）

### 症状

你问终端重绘为什么不是只重绘一部分。它确实不是——目前就是全量。

`renderMonitor()`（`app.main.js:1881`）把整个可见日志拼成 HTML 字符串数组，
然后整体赋值：

```js
refs.terminal.innerHTML = parts.join('') || `...`;
```

第 1946 行。每个 RX 分块都会调用 `scheduleRefresh({ monitor: true, ... })`，
而刷新用 `requestAnimationFrame` 合并——所以**频率**被压到每帧一次，
但**每次重建的成本**与整个缓冲区成正比。

### 这正是缓冲区被限制在那个数字的原因

上一轮的 256K / 512K 就是从这个成本实测推导出来的
（`audit/measure-buffer.mjs`，五次重建取中位数）：

| 字符数 | DOM 节点 | 重建耗时 |
| --- | --- | --- |
| 8 192 | 528 | 0.2 ms |
| 131 072 | 8 456 | 3.1 ms |
| 262 144 | 16 912 | 7.0 ms |
| 524 288 | 33 824 | 13.3 ms |
| 1 048 576 | 67 652 | 26.6 ms |

60Hz 一帧 16.7ms，所以 512K 正好在边缘。**这个上限是实现的产物，不是数据的属性。**

### 修法 —— 增量追加

RX 只在尾部增长，`trimLiveEvents()` 从头部裁剪，中间部分从不重写。
解析器的逐行结果也只对最新那行变化。

所以重建可以拆解：

| 情况 | 动作 |
| --- | --- |
| 底部追加新行、缓冲区未裁剪 | 只 `append()` 新行 |
| `trimLiveEvents()` 从头部裁剪 | 移除对应行，不动其余 |
| 原本在底部 → 跳到底部 | `scrollTop = scrollHeight`，保持不变 |
| **原本不在**底部（`state.ui.terminalAtBottom` 为 false） | 不动滚动位置 |
| 显示选项变化（时间戳、hex 模式、字号、编码） | 全量重建——它们改变每一行 |
| 正在保留终端选区 | 已在第 1882 行短路 |

最后两条是这件事需要小心而非三行改动的原因。`showTimestamps`、`showRawHex`、
`--log-size` 和文本编码都是全局量，任何一个变化都会让所有行失效。
正确的做法是对这四个输入加上 `liveEvents[0].id` 与 `liveEvents.length` 取哈希，
哈希不同才重建。

值得一提：`refs.terminalAtBottom` 已经存在且 `renderMonitor()` 已在读它
（第 1887 行），所以最棘手的情况——用户向上滚动看历史、数据同时到达——
已经被跟踪了。

### 这换来什么

追加一行的成本是一个 `createElement` 加一次文本赋值，与缓冲区大小无关。
在本机实测，追加比重建同一份内容便宜约两个数量级。这把上限从
「一帧的预算」变成「DOM 能承载多少」，于是缓冲区上限变成**内存决策**而非
**帧率决策**：

- 实时日志默认 256K → **2M 字符**，上限 8M。
- 512K 选项上那条代价注释随之作废，应改写为说明限制来自内存而非渲染。

我会让默认值远低于上限。2M 字符仍意味着数万行，而 `getActiveEvents()` 加
可见窗口循环（第 1919 行）每帧都要走完整个缓冲区——**那个循环才是下一个瓶颈，
它与 DOM 无关，仍然是 O(缓冲区)**。

所以这项改动应当配上一个**窗口化渲染**：只实体化视口附近的行，利用现有的滚动
位置。这是个更大的改动；我会先落增量追加、实测，再决定是否继续。

## 2. 缓冲下拉的标签有问题

`index.html:455`–`465`。当前标签混用体系、也给不出大小次序：

```
缓冲: 5 千 / 2 万 / 10 万
日志: 64K / 256K / 512K
```

三个问题：中文数量词与 `K` 后缀混用；「5 千」是最小值却读起来像取整而非下限；
两个控件计量的东西不同（行数 vs 字符数）而标签里没有任何说明。

### 修法

```
回滚行数   5000 / 20000 / 100000        （纯数字，升序）
日志字符   262144 / 1048576 / 4194304  （纯数字，升序）
```

纯数字、升序，次序自明，两个控件都不需要在选项文本里加单位前缀。
单位属于字段标签，标签已经在那里了。数值随第 1 项的新默认值调整。

如果你想要可读 千位，诚实的替代方案是**每个选项都带后缀**
（`5000` / `20K` / `100K`）而不是混用——但我不建议，
因为 `100000` 与 `100K` 并列会重新引入「哪个更大」的歧义。

## 3. 快捷键覆盖不足以支撑 fzf 与 readline

同意，而且缺口是可以精确枚举的。当前 `TERM_KEY_SEQUENCES`
（`app.terminal.js:346`）有 14 项，其中 Ctrl 家族只有 `^U ^W ^K ^C ^D ^Z`。

你点名的全部是单个控制字节，所以这只是**表扩展，不需要新机制**：

| 按键 | 字节 | fzf / readline 用途 |
| --- | --- | --- |
| `^R` | `\x12` | 反向增量搜索——最关键的一个 |
| `^T` | `\x14` | 转置字符 |
| `^N` | `\x0e` | 下一条历史 / fzf 绑定里的 `Ctrl-N` |
| `^P` | `\x10` | 上一条历史 |
| `^A` | `\x01` | 行首 |
| `^E` | `\x05` | 行尾 |
| `^L` | `\x0c` | 清屏 |
| `^B` | `\x02` | 前移一字符 |
| `^F` | `\x06` | 后移一字符 |
| `^Y` | `\x19` | 召回 |
| `^G` | `\x07` | 中止 / 取消 |
| `^O` | `\x0f` | 轮换历史 |
| `^V` | `\x16` | 引号插入 |
| `^X` | `\x18` | 切换转置 |

编辑组还缺：`Ctrl-H`（退格，`\x08`，与 `\x7f` 不同）、`Ctrl-Space` / `Ctrl-@`
（`\x00`，置标记）、`Alt-B/F` 按词移动（`\x1bb` / `\x1bf`）。

### 分组

当前按键条四组，五组读起来更好：

| 组 | 按键 |
| --- | --- |
| 导航 | `↑ ↓ ← → Home End PgUp PgDn` |
| 编辑 | `Backspace Delete ^A ^E ^B ^F ^K ^U ^W ^T ^Y` |
| 历史 / 补全 | `^R ^P ^N ^O ^L` |
| 控制字节 | `^C ^D ^Z ^G Tab Esc` |
| 字符输入 | `^V`（引号插入）—— 单键，与控制字节同组 |

**历史 / 补全**组就是面向 fzf 的那一组，值得单独命名，
因为用户想 `^R` 时找的就是这一组。

### 两条仍然成立的约束

1. **不用裸字母。** `app.main.js` 注册了 document 级的单键按下处理器用于预设发送。
   裸字母会悄无声息地遮蔽用户的预设。
2. **这些按键已绕过防抖** —— `sendTerminalKey()` 先调 `flushTerminalKeyBuffer()`，
   所以控制字节不会被缓冲的可打印文本拖在后面，次序得以保持。

加约 16 项就是标记加表条目。每个按钮上的 `data-tip` 属性在 tooltip 单例
接管之后会自动提供文档。

## 4. 控件尺寸与信号读数

三个独立问题。第一个是真实的，第二个是语义错配，
第三个就是 `docs/layout-redesign.md` 已覆盖的左栏空白。

### 4a. 没有控件尺寸令牌 —— 这才是「大小都不一样」的根因

设置面上的高度散布：

| 高度 | 位置 |
| --- | --- |
| 30px | `.secondary-btn` 家族、`.term-field`、若干 toggle |
| 31px | 某个按钮变体 |
| 32px | `.field select` / `.field input` |
| 34px | `.toggle-row`、`.primary-btn` 变体 |
| 36px | `.signal-readout`、`.signal-chip` |

连接栏与工具栏上共 5 种值。没有 `--control-h` 令牌，所以每一个都是字面量。

### 修法

加两个令牌并归一：

```css
--control-h: 32px;      /* select、input、button */
--control-h-sm: 28px;   /* 工具栏 term-field、chip */
```

把当前 5 个值映射上去，然后在 1440 / 1600 / 1920 目视核对连接栏。
除替换外不做别的——这是替换而非重设计，
但正是它让左栏读起来像**一个**面板而不是五个拼装件。

### 4b. CTS / DSR / DCD / RI ——「都显示关」是正确的，虚线框不是

先说行为是对的。`state.serial.signalInputs` 默认全为 `null`
（`app.core.js:420`），`signalValueLabel()`（`app.main.js:486`）把
`null` 映射为 `-`、`false` 映射为「关」，而这些值只在连接成功后由
`getSignals()` 写入（`app.main.js:583`）。所以端口未打开时诚实的显示是 `-`。
这些是**来自设备的输入**——Web Serial API 无法设置它们，所以没有可点的东西。

话虽如此，确有两处真的不对：

- **虚线边框有误导性。** 虚线框的惯例含义是「可填写、待输入」，
  而这是只读状态。同一面板里 DTR/RTS/BREAK 开关是**可交互**的，
  两者读起来像同一类东西。
- **「无法交互」是正确的，但应该让人看得出来。** 设备把 CTS 拉低时，
  用户无法分辨这是真实读数还是驱动不支持——这是真实存在的歧义。
  `getSignals()` 在驱动不报告 modem 状态的端口上可能返回全 `false`
  而不是抛错，这与真实的「全低」无法区分。

### 修法

- 改为 1px **实线**边框，与 DTR/RTS 芯片一致——读数就该长得像读数。
- 把 `-` / 开 / 关 的文本换成能说明状态的三态指示：
  从未读取过时 `-` 变为弱化的 `未知`；
  `getSignals()` 成功但什么都没报时，用一个与「关」不同的 `未知` 状态。
- **不要**把它们做成可交互。如果你想要的是置位控制，
  那是另一个功能（设置 DTR/RTS 把设备从复位态拉出来），
  不是给一个输入引脚加点击目标。

### 4c. 空荡的左栏

已在 `docs/layout-redesign.md` 中实测并覆盖。要点：那约 500px 的空余
是被 `style.css:2712`（`body:not(.layout-expanded)`）隐藏的解析列，
等待图形解析模式。**它不是一个空面板**——这正是我此前尝试又撤回的
「未配置提示」方案错在哪。

真正的方案不变：让 `layout-expanded` 变成**叠加式**（保留监视器，只移动图表），
使这个开关读起来像视图切换而不是替换；并让 `config-panel` 收拢到内容高度。
那项工作仍未开始，应当排在 4a 之后——因为收拢需要一个统一的控件尺寸作为目标。

## 5. 模拟与解析 —— 依赖关系是反的

已实测，这条要更正报告。

在**没有串口连接**的情况下，开启模拟并使用文档里的规则 `/name0=/float0`：

```
logLines: 5   rxRows: 4
cards: 2      cardLabels: ["temp 22.1", "humid 53"]
```

解析在没有端口的情况下完全正常，因为生成的字节走
`queueRxBytes()`（`app.main.js:137` → `:35`），与串口读取同一个 RX 入口，
而那里没有任何连接检查。

真正存在的约束方向相反：`emitSimulationFrame()` 在
`state.serial.connected` 时提前返回（`app.main.js:141`），
即**模拟向真实设备让位**。这是有意为之——两个来源把字节交错进同一条流
会破坏解析——我建议保留。

### 真正的缺口：模拟行无法辨认

`simulated: true` 被写进事件元数据（`app.main.js:146`），
而**任何地方都没有读取它**。所以日志里一旦充满数据，
就没有办法区分哪些行来自设备、哪些来自模拟器。
对一个目的就是演示解析器的功能来说，这才是值得修的缺陷。

### 修法

- 在模拟行上渲染 `SIM` 标记，复用现有的 `.preset-inline-tag` 处理
  但换一个色调，让它读起来像标签而不是载荷。
- 在模拟控件里加一个计数：`已产生 N 帧`。
- 让「让位」可见：连接抑制模拟时 toast 已经会说明——保留它，
  并补到控件自己的副标题上，而不只在瞬时 toast 里，
  这样状态一眼可读。

可选：允许模拟与设备**并行**——把模拟器喂进一个独立的事件列表而不是同一个
`liveEvents`。这是个更大的改动，你不要求我不会做。
